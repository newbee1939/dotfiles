# Extract Learnings（学びの抽出）

今日のすべてのセッションから学びを拾い、**別の場面でも発火する原則**まで抽象化する。

## 1. 今日のセッションを集める
```bash
# 1 ファイル = 1 セッション（-mtime -1 は「今日」ではなく「24 時間以内に更新」。
# 前日夜のセッションも混ざるので、タイムスタンプで今日の分だけ拾う）
find ~/.claude/projects -name '*.jsonl' -mtime -1

# 中身のテキストだけ読む
jq -r '.message.content? | if type=="array" then map(.text // empty) | join("\n") else . // empty end' <file>
```
長いセッションは全部読まず、詰まった箇所・やり直した箇所を拾う。

## 2. 学びを拾う
- うまくいかず**やり直したこと**と、その原因
- 知らなかった仕様・挙動・ツール
- 判断に迷った点と、最終的にどう決めたか
- 進め方やコミュニケーションで効いたこと / 効かなかったこと

## 3. 抽象化する
抽象化の狙いは「次に同じ状況で使えること」**ではない**。それは下限にすぎない。狙いは**転移**——ツールも場面も違うのに、**構造が同じだから発火する**状態にすること。

そのために、原則からは**固有名詞（ツール名・サービス名）と今日の状況を消し、代わりに「どんな条件が揃ったときに効くか」を書く**。

- ✗ 「jq の使い方を学んだ」（具体で止まっている）
- ✗ 「事前確認が大事」（一般論すぎて行動に落ちない）
- △ 「jq に通す前に中身を見る」（ツールに貼り付いていて、jq のときしか思い出せない）
- ○ 「**出力仕様が保証されていないものを機械的に加工するときは、先に生の中身を 1 件見る**」（`curl | grep`・CSV・ログ基盤でも発火する）

書けたら「**今日と全然違う場面を 1 つ挙げて、そこでも効くか**」を自問する。効かないならまだ具体に寄りすぎ。

## 4. 一段下まで降りる
学びごとに「**なぜそうなるのか**」を、その下の層（OS / ファイルシステム / ネットワーク / プロトコル）まで降りて書く。表面の挙動だけ覚えても転移しないが、仕組みが分かっていれば初見の事象にも効く。

- 終了コード・シグナル・エラーメッセージは、**OS が何を伝えようとしているか**まで開く（例: `exit 137` = メモリ超過で OS がプロセスを強制終了）
- 一次情報（公式ドキュメント / 仕様 / `man` / ソース）で裏を取る。**推測なら「未確認」と明示する**
- 降りきれなかったものは正直に「説明できなかったこと」に回す。分かったふりで埋めない

## 5. 出力
学び 1 個 = `##` セクション 1 個で、**3〜5 個に絞る**。タイトルは**何の話か一言で**分かるものにする。
```markdown
# 今日の学び（YYYY-MM-DD）

## <学びのタイトル>

### 具体的な学び
<今日実際に何が起きて、何が分かったか。ログ・エラー・コマンドなど事実で書く>

### なぜそうなるのか（一段下）
<その下の層で何が起きているか。裏を取った一次情報のリンクを添える>

### 具体的な学びを抽象化した学び
<固有名詞を消し、どんな条件で効くかで書く。別の場面でも発火する言い方。1〜2 行>

## 一段下が説明できなかったこと
- <今日触った技術で、その下の層を説明できなかったもの 1〜2 個>

## 次に試すこと
- <1〜2 個>
```
「一段下が説明できなかったこと」は翌日の `deep-dive` のネタになる。

## 原則
- 全部書くと何も残らない。**捨てる**ほうが大事。
- 教科書的な一般論は書かない。今日の自分の経験から出たものだけ。
- 「動いたからヨシ」で止めない。**なぜ動いたかを説明できて初めて学び**。
