# Review PRs（レビュー待ちを優先度順に潰す）

溜まった **自分レビュー待ちの PR** を、優先度順に 1 件ずつ処理する。
目的は 2 つ: **件数を減らすこと** と、**レビューした PR の中身が自分の頭に残ること**。

## 1. 集める

```bash
gh search prs --review-requested=@me --state=open \
  --json number,title,repository,url,createdAt,updatedAt,isDraft --limit 50
```

draft は除外。各 PR のメタを取る:

```bash
gh pr view <番号> --repo <owner/repo> \
  --json additions,deletions,changedFiles,files,statusCheckRollup,mergeable,body,author,url
```

## 2. 並べる

まず **足切り**（読まずに返す）を分ける。ここを先に片付けると残り件数が減る。

- CI 失敗中 / コンフリクト中 → 読まない。「CI を通してから見ます」の 1 行コメント案だけ出す
- draft → 対象外

残りをスコア順に並べる:

1. **待たせている時間**（`createdAt` が古いほど上。他人をブロックしているものが最優先）
2. **リスク**（`terraform/` / migration / auth・権限・シークレット / `.github/workflows/` / k8s manifest を触っている）
3. **小ささ**（小さいものを先に潰して件数を減らす）

表で出す。

```
| # | PR | リポジトリ | 待ち日数 | 規模 | リスク | 深度 |
```

## 3. 深度を決める

全 PR を同じ深さで見ると終わらない。**PR ごとに深度を提案し、ユーザーが上げ下げする。**

| 深度 | 対象 | やること |
| --- | --- | --- |
| **L1 スキップ** | 依存 bump / 自動生成 / typo / 設定値だけ | 差分の性質を確認して approve 案を出す |
| **L2 通常** | 見慣れた領域の変更 | 変更意図・設計・影響範囲を要約 → 指摘候補 → ユーザーが判断 |
| **L3 仮説→答え合わせ** | リスク高 / 知らない領域 | 下記の手順（答えを先に出さない） |

**L3 は 1 日 2〜3 件が現実的。** それ以上は L2 に落とす。

## 4. 1 件ずつレビューする

**着手時に必ず PR の URL を提示する**（`https://github.com/<owner>/<repo>/pull/<番号>`）。ブラウザで並べて見られるようにする。

### 下ごしらえ（全深度共通）

```bash
gh pr diff <番号> --repo <owner/repo>
```

- PR 説明とリンクされた issue / チケットを読む
- **既存の未解決スレッドを先に取る。** 他人が既に指摘済みのことを重複して書かない

```bash
gh api graphql -f query='
{ repository(owner:"<owner>", name:"<repo>") {
    pullRequest(number: <番号>) {
      reviewThreads(first: 50) { nodes {
        isResolved path line
        comments(first: 10) { nodes { author { login } body } }
      } }
    } } }'
```

（解決状態 `isResolved` は GraphQL にしかない。REST のコメント API は返さない）

### L1 の手順

差分が本当に機械的か（generated ファイル / lockfile / バージョン文字列のみ）を確認し、approve 案を出す。
**少しでも手書きロジックが混ざっていたら L2 に上げる。**

### L2 の手順

1. 変更意図（PR 説明ではなく **差分から読み取れること**）を要約
2. 設計上の判断ポイントと影響範囲を挙げる
3. 指摘候補を出す → ユーザーが採否を決める

### L3 の手順（仮説 → 答え合わせ）

**答えを先に言わない。** 順番を守る。

1. 材料だけ出す: 変更ファイル一覧、各ファイルの役割、呼び出し関係、PR 説明
2. 聞く: **「この変更は何を達成する？ どこが壊れやすいと思う？」**
3. ユーザーの仮説を **当たり / 惜しい / 外れ** で先に判定する
4. **ズレた箇所だけ**掘る。該当コードと一次情報（公式ドキュメント / 仕様 / ソース）で裏を取る
5. 腹落ちしてから指摘候補に進む

### 見る観点（L2 / L3 共通）

- **意図**: PR 説明と差分が一致しているか。説明にない変更が混ざっていないか
- **境界**: 異常系、null / 空、上限、タイムアウト、並行アクセス
- **影響**: 変更した関数・設定の呼び出し元を **grep で実際に確認する**（想像で済ませない）
- **運用**: ロールバックできるか。移行手順の順序。ログ・メトリクスは足りるか
- **CI と lint が言えることは言わない。** 設計・命名・責務・運用リスクに絞る

## 5. コメントを投稿する

コメント案（inline 指摘 + 総評）をターミナルにまとめて出す → **ユーザーが承認 → 投稿**。

**必ず Reviews API で 1 リクエストにまとめる。** 行ごとに `/pulls/<番号>/comments` を叩くと指摘の数だけ作者に通知が飛ぶ。

```bash
gh api repos/<owner>/<repo>/pulls/<番号>/reviews -X POST --input - <<'JSON'
{ "event": "COMMENT",
  "body": "<総評>",
  "comments": [
    {"path": "<ファイル>", "line": <行>, "side": "RIGHT", "body": "<指摘>"}
  ] }
JSON
```

- `event`: `COMMENT`（判定なし） / `REQUEST_CHANGES`（修正要求。ブランチ保護次第でマージをブロック） / `APPROVE`
- `COMMENT` と `REQUEST_CHANGES` は `body` が必須
- `event` を省くと **PENDING**（下書き）。判断を保留して指摘だけ溜めたいときに使う
- 複数行にまたがる指摘は `start_line` を足す

approve は **ユーザーが指示したときだけ**実行する:

```bash
gh pr review <番号> --repo <owner/repo> --approve --body '<本文>'
```

深く見たいときは Claude Code 標準の **`/code-review <PR番号>`** を呼ぶ。バグ検出を機械的に走らせて、その結果を上の観点と突き合わせる。

## 6. 記録して次へ

処理した PR を `~/.claude/review-log.md` に 1 行追記する。中断しても続きから再開できる。

```
- 2026-08-10 owner/repo#123 L2 コメント3件 / 承認待ち
```

再開時はこのファイルを読み、済みの PR を一覧から除いてから 2 に戻る。

## 原則

- **CI と bot が言えることは言わない。** 人間が見る価値があるのは意図・設計・運用リスクだけ
- **「LGTM」だけで通さない。** 何を確認して通したかを 1 行残す
- **わからないものを approve しない。** 質問を投げて次の PR へ進む（自分を止めない）
- 大きすぎる PR は、読み切る前に **分割を依頼する**のが最も速い
