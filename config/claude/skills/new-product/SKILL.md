# New Product（個人開発の立ち上げ）

**設計と最終判断は人間、その間は自動**の半自動フロー。人間が判断するのは §1〜3 と各 PR のマージだけ。
ここが甘いと §4 で必ず崩れるので飛ばさない。

- リポジトリ共通の設定 → [`references/repo-baseline.md`](references/repo-baseline.md)（コピペ用）
- この skill の育て方 → §7

3 つのドキュメントはリポジトリ直下に置き、冒頭に**ステータス行**を書いて凍結する。書かないと実装中に AI が方針を変える。

```
> **ステータス: 確定版。** 方針を変えるときは本ファイルを直し、PR で履歴を残す。
```

## 0. 全フェーズ共通の原則

**1. 検証できないものは作らない。** Claude は「done に見えたら止まる」ので、**Claude 自身が回せる合否判定**（テスト・ビルドの終了コード・スクショ比較）が無いと検証役が毎回あなたになる。DoD は「動くこと」ではなく「`npm test` が exit 0」。主張ではなく**実行したコマンドと出力**を出させる。

**2. 唯一の真実は 1 箇所。** 同じ情報を 2 箇所に書くと必ずドリフトする。片方には「詳細は◯◯」とだけ書く。

**3. コンテキストは有限。** フェーズごと・タスクごとに `/clear` して新セッションで始める（ドキュメントが残るので引き継げる）。調査は subagent に投げる。同じ間違いを 2 回直させたら、直さずに `/clear` してプロンプトを書き直す。

**4. ドキュメントは短く書く。** 以降のテンプレートは**枠であって、埋める義務ではない**。長いドキュメントは読まれず、更新されず、すぐ実装とズレる。

- **該当しない節は、空にせず節ごと消す。** 「未定」「特になし」と書かない。
- **判断が変わらない一文は削る。** 残すのは「後で自分が迷ったときに答えを出せる記述」だけ。
- 分量の目安 — CONCEPT.md: 1 画面 / ARCHITECTURE.md: 2〜3 画面 / PLAN.md: 1 タスク 3 行。
- **迷ったら書かない。** 足りなければ後から足せる。

## 1. CONCEPT.md（何を作るか）

**まず Claude にインタビューさせる。** 自分で書き出すより速い:

```
<1 行のアイデア> を作りたい。AskUserQuestion で私にインタビューして。
技術・UX・エッジケース・トレードオフを、当たり前のことは飛ばして難所だけ掘って。
埋まったら CONCEPT.md に書き出して。
```

**手を動かす前に需要と競合を調べ、URL を貼る**（「たぶんある」で終わらせない）:

1. **同じものがあるか** — GitHub・Product Hunt・Zenn / Qiita
2. **困っている人の声があるか** — X・Reddit・Stack Overflow。自分以外に 1 人もいなければ需要は自分だけ
3. **お金が動いているか** — 有料サービスの存在は需要の証明

```
# <プロダクト名>
## 背景      なぜ自分が欲しいか（弱いと続かない）
## 課題      誰が、どんな場面で困っているか
## 需要      困っている人がいる証拠（URL）
## 競合      既にあるもの / それでも作る理由
## 解決策    どう解くか（2〜3 文）
## スコープ外  やらないこと（曖昧だと無限に膨らむ）
## 完成の定義  「これが動いたら v1 完成」の 1 文
```

- **競合ゼロは良い兆候ではない。** 需要が無いか、誰かが試して失敗している。理由を言えるまで掘る。
- **競合ありは着手 OK。** ただし「自分の版はここが違う」を 1 文で言えること。
- **需要が自分だけでも作ってよい。** ただし CONCEPT.md にそう書く。
- **v1 は 1 機能。** 迷ったら削る。

## 2. ARCHITECTURE.md（どう作るか）
`/clear` して CONCEPT.md を読ませる。**選択肢とトレードオフを出し、選ぶのはユーザー。**

```
# アーキテクチャ
## 設計原則    守る判断基準 3〜6 個（迷ったらここに戻る）
## 全体の流れ  トリガー → 処理 → 出力
## ファイル構成 どこに何を置くか。「作らないもの」も書く
## 技術選定    採用 / 捨てた対抗馬 / 理由 / 決定日 / 可逆か
## データ      扱うデータと保存場所。個人情報を持つか
## 外部連携    使う API と、その料金・上限
## セキュリティ 下記のうち既定から外れる判断だけ
## 運用        デプロイ方法、壊れたと気づく手段
## 落とし穴    着手前に先回りして書く
## ロードマップ Phase ごとの DoD
```

**技術選定を速くする**
- **可逆な決定に時間をかけない。** SSG・ホスティングは差し替えられる。**不可逆なのはデータの持ち方だけ**なので、悩む時間は全部そこに使う。
- **既定スタックを 1 つ決めておき、理由が無ければそれを使う。** 毎回選び直さないのが最大の時短。
- 決定は**捨てた案と理由**まで書く。半年後に同じ検討を繰り返さない。
- 新しいライブラリは**公式ドキュメントを読ませてから**書かせる。学習データが古いと存在しない API を書く。Context7 のような最新ドキュメント MCP を入れると事故が減る。
- **`AGENTS.md` を真実にし、`CLAUDE.md` は `@AGENTS.md` の 1 行にする。** AGENTS.md は Codex / Cursor / Copilot なども読む共通規格で、乗り換えコストが下がる。

**落とし穴は実際に踏む地雷を書く**（架空のリスクは書かない。公式ドキュメントで裏を取る）。過去の例:
- Actions の `GITHUB_TOKEN` で push したコミットは**他のワークフローを起動しない**（無限ループ防止の仕様）。`workflow_run` で受ける。
- GitHub Pages はサブディレクトリ公開。`base` を忘れると CSS が全部 404。
- Actions の実行環境は **UTC**。cron は JST から 9 時間引く。

**セキュリティ** — 設定は [`repo-baseline.md`](references/repo-baseline.md) をそのまま入れる。ここに書くのは外れる判断だけ:
- シークレットの置き場（リポジトリには入れない）と、公開範囲・認証方式。
- **CI で AI エージェントを動かすなら、信用できない入力と secrets を同じジョブに置かない。** Issue タイトル・PR 本文は攻撃者が書ける文字列で、エージェントはそれを指示として読む（2026 年 4 月、複数の AI レビュー Action が secrets を PR コメントに出力させられた）。フォーク PR では走らせない。
- **自分の鍵で外部 API を叩かせるなら上限を先に決める。** 個人開発で一番痛いのは侵入より請求書。

## 3. PLAN.md（実装計画）
`/clear` して CONCEPT.md と ARCHITECTURE.md を読ませる。**AI が迷わず上から実行できる粒度**まで割る。曖昧なら §1〜2 に戻る。

```
## P1 — <Phase 名>
**Goal**: <これができたら次の Phase へ>

### P1-1. <タスク名>
- [ ] **やること**: <具体的な手順。コマンドはそのまま書く>
- **成果物**: <ファイルパス>
- **DoD**: <実行して確かめるコマンド / 目視手順>
```

- 1 タスク = 1 PR 相当。依存順に並べる。
- **DoD は検証可能な形で**（原則 0-1）。曖昧なタスクは必ず「できたつもり」で返ってくる。
- 完了は `- [x]`、やめたものは `- [~]` ＋理由（消さない）。想定と違ったら **`実績:`** を追記する。ここが次の資産になる。
- 各 Phase の末尾に**振り返り**タスクを置く。
- **P1-1 は必ず「足場を入れる」タスク。** 中身は [`repo-baseline.md`](references/repo-baseline.md)。後から入れるのは全部直すことになるし、たいてい入らない。
- 最初の機能タスクは**動く最小の骨組み + デプロイ**。先に道を通す。
- **LLM を使う機能があれば eval も P1 に入れる。** 入出力ペアを 20〜50 件書いて CI で回すだけでいい（promptfoo など）。プロンプトを 1 行変えただけで静かに壊れるのを防ぐ。**本番で失敗した入力を足していく**のが一番効く。
- 書き方に迷ったら `superpowers:writing-plans`。

**実装前に 2 つ回す**（ここでの 10 分が数時間を救う）:
1. **曖昧さの洗い出し** — 「判断に迷う箇所、前提が書かれていない箇所を列挙して」
2. **整合チェック** — 「完成の定義を満たすタスクが揃っているか、ARCHITECTURE.md と矛盾がないか」。**別セッションで**（書いた本人には穴が見えない）

→ ユーザーが PLAN.md をレビューする。**承認されるまで実装に進まない。**

## 4. 実装（半自動で流す）
**タスクごとに新セッション**を開き、該当タスクだけを渡す。**1 タスク = 1 PR。人間がレビューできる大きさを超えたら割り直す。**

1. ブランチを切る（`start-task`）。方針が自明でなければ **plan mode（`Shift+Tab`）**で先に計画させる。1 文で diff を説明できるなら飛ばす。
2. 実装する（ロジックは `superpowers:test-driven-development`）。
3. **DoD のコマンドを実行**して出力を確認する。通っていないのに次へ行かない。
4. **セルフレビュー**: `code-review` skill（別コンテキストの subagent が diff だけを見る）を回し、`git diff` も自分で読み直す。**指摘は PR を出す前に直す。**（GitHub に自動でコメントするマネージド版の Code Review は Team / Enterprise 限定・1 レビュー $15〜25。個人開発ではローカルのこれで足りる。2026-08 時点）
5. PLAN.md を更新して `commit` → `create-pr`（ドラフト）。**URL を出して止まる。**

**速くするための道具**

| 道具 | 使いどころ |
|---|---|
| `/goal` + auto モード | 「テストが通り lint がクリーンになるまで」等の合否条件を渡すと、満たすまで自動で回る。**条件は Claude の出力から判定できる形で書く**（評価役はコマンドを実行しない） |
| `ultracode`（dynamic workflows） | 「全ファイルに同じ監査をかける」「型エラーが消えるまで直し続ける」など**数十体規模の並列作業**。中間結果がスクリプト側に残るのでコンテキストを食わない。`/workflows` で `s` を押すとコマンドとして保存できる。トークンを大量に使うので小さい範囲で試してから |
| ブラウザ MCP（Playwright / Claude in Chrome） | **UI に検証ループを効かせる。** 「スクショを撮って元デザインと比較して直せ」が回るようになる |
| hook | 絶対に毎回やらせたいこと。CLAUDE.md の指示は努力目標だが hook は決定的（例: 編集後に必ず lint） |
| git worktree | 並行作業は **2〜3 本まで**。それ以上はレビューが追いつかず自分が詰まる |

**ここから先は人間**
- **Ready もマージも人間。** Claude は `gh pr merge` を実行しない。
- マージを確認してから次のタスクへ（PR を積むと衝突する）。**待ち時間に先行実装しない** — 計画の正しさはマージされた実物を見て分かる。
- 指摘には `superpowers:receiving-code-review` で対応し、**description も最新化**する。

**その他**
- 計画と違う実装が要るなら、**PLAN.md（必要なら ARCHITECTURE.md）を直してから**実装する。
- **認証・権限・公開範囲・CI を触る PR は敵対的検証にかける。** 新規セッションで「レビューして」ではなく**「反証を試みよ」**と指示し、一次情報で裏を取らせる。ただし**レビュー役は探せば必ず何か見つける**ので「正しさと要件に関わるものだけ」と縛る。採否は人間が決める。
- **scaffold コマンド（`create-*` 系）は既存ファイルを上書きする。** 別ディレクトリで生成して必要なものだけ持ち込む。

## 5. 出す・測る・畳む
量産で怖いのは、価値の無いものが増えて保守コストを払い続けること。**作り終わりはゴールではない。**

1. **v1 が動いたらその日に公開する。** 完成度を上げてから出すと、たいてい出さないまま終わる。
2. **「これが起きたら成功」を 1 つだけ決めて CONCEPT.md に追記する。** 自分が毎日使う / 誰かが使う / 記事にできる、何でもいいが**測れる形**にする。
3. **1 か月後に見る。** 満たしていなければ、畳むか、v2 の仮説を 1 つだけ立てて作り直す。惰性で機能を足さない。
4. **畳むのは失敗ではない。** README に「アーカイブ。理由: 〜」と 1 行書いて残す。学びと足場は次に持ち越せる。
5. **手を入れない期間を作る。** Dependabot の月 1 PR だけ見て放置できる状態が「持続可能」の定義。

## 6. 量産する
持ち越すのは**ドキュメントの型と足場だけ**。中身は毎回ゼロから書く。

- 振り返りを読み返す。**詰まる場所はたいてい同じ**（スコープ外が甘い / DoD が曖昧 / 二重管理）。
- 繰り返す手順が見つかったら `find-automation` で skill 化する。
- **同時に動かす新規プロダクトは 1 つまで。** 並行させていいのは 1 プロダクト内のタスクだけ。

## 7. この skill を育てる（Claude へ）
**この skill は完成品ではない。** 使うたびに更新候補を探し、**その場で提案する**（勝手には書かない）。

提案するタイミング — 次のどれかに当てはまったとき、作業の区切りで 1 行で聞く:
- PLAN.md の「実績」が次のプロダクトでも起きそう
- **同じ落とし穴を 2 回踏んだ**（1 回目は事故、2 回目はパターン）
- 公式ドキュメントで裏を取った**新しい事実**を見つけた（憶測は書かない）
- ユーザーが**同じ指摘を 2 回した**（skill に書かれていない証拠）

書き方:
- **原則は SKILL.md、コピペする設定は `references/`。** SKILL.md が長いほど肝心の指示が薄まる。
- **陳腐化する記述には日付を書く**（バージョン・料金・「〜が最新」）。
- 追記より**削除を優先**。守られていないルール、当たり前になったルールは消す。
- 半年に一度、ツール名とバージョンが現実と合っているか見直す。
