# New Product（個人開発の立ち上げ）

**設計に人間の判断を集約し、実装は自動で流す**ための skill。
判断が要るのは 1〜3 だけ。ここが甘いと 4 で必ず崩れるので、**先に進みたくなっても飛ばさない**。

成果物はプロダクトのリポジトリ直下 `docs/` に置く。

## 1. CONCEPT.md（何を作るか）
ユーザーに 1 行でアイデアを聞き、**質問して埋める**（勝手に決めない）。

```
# <プロダクト名>
## 課題      誰が、どんな場面で、何に困っているか
## 解決策    それをどう解くか（2〜3 文）
## スコープ外  今回やらないこと（重要。ここが曖昧だと無限に膨らむ）
## 完成の定義  「これが動いたら v1 完成」と言える 1 文
```

- **v1 は 1 機能に絞る**。迷ったら削る。
- 既存サービスとの違いが言えないなら、まだ着手しない。

## 2. ARCHITECTURE.md（どう作るか）
CONCEPT.md を読んだ上で構成を決める。**選択肢とトレードオフを出し、選ぶのはユーザー**。

```
# アーキテクチャ
## 技術選定    言語 / フレームワーク / ホスティング / DB。それぞれ「なぜ選んだか」を 1 行
## 構成        主要コンポーネントと処理の流れ
## データ      扱うデータと保存場所。個人情報を持つか
## 外部連携    使う API・サービスと、その料金/上限
## セキュリティ 認証方式 / シークレットの置き場 / 公開範囲
## 運用        デプロイ方法、壊れたと気づく手段
```

- **シークレットをリポジトリに入れない**前提を最初に決める（環境変数 / Secret Manager）。
- 個人開発では「自分が止めたくなったら止められるか」も見る（月額が積み上がる構成を避ける）。

## 3. PLAN.md（実装計画）
ここが本体。**AI が迷わず上から実行できる粒度**まで割る。曖昧さが残っていたら 1〜2 に戻る。

```
# 実装計画
- [ ] 1. <タスク名>
      ゴール: <終わったら何ができているか>
      触るファイル: <パス>
      完了条件: <実行して確かめるコマンド / 目視の手順>
```

- 1 タスク = 1 コミットの粒度。依存順に並べる。
- **完了条件は必ず検証可能な形**にする（「動くこと」ではなく「`npm test` が通る」）。
- 最初のタスクは「動く最小の骨組み + デプロイ」。先に道を通してから肉付けする。
- 計画の書き方に迷ったら `superpowers:writing-plans` を使う。

→ ここでユーザーに PLAN.md をレビューしてもらう。**承認されるまで実装に進まない。**

## 4. 実装（自動で流す）
PLAN.md を上から消化する。1 タスクごとに:

1. 実装する（テストがあるものは `superpowers:test-driven-development`）。
2. **完了条件のコマンドを実際に実行**し、出力を確認する（通ってないのに次へ行かない）。
3. PLAN.md のチェックボックスを埋め、`commit` skill でコミットする。

- コンテキストが枯れるので、**独立したタスクは sub-agent に投げる**（`superpowers:subagent-driven-development`）。
- 計画と違う実装が必要になったら、勝手に進めず **PLAN.md を直してから**実装する。
- 全部終わったら `create-pr` skill。

## 5. 量産する
次のプロダクトも同じ 1〜4 を回す。振り返りは 1 行だけ:

- **前回どこで詰まったか**（たいてい CONCEPT のスコープ外が甘い、か PLAN の完了条件が曖昧）。
- 繰り返し出てくる手順が見つかったら `find-automation` skill で skill 化する。
