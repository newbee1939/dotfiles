# New Product（個人開発の立ち上げ）

**設計と最終判断を人間が持ち、その間を自動で埋める**ための skill（全自動ではなく**半自動**）。
判断が要るのは 1〜3 と、各 PR のマージ。ここが甘いと 4 で必ず崩れるので、**先に進みたくなっても飛ばさない**。

3 つのドキュメントはリポジトリ直下に置く。各ファイルの冒頭に**ステータス行**を書く:

```
> **ステータス: 確定版。** 方針を変えるときは本ファイルを直し、PR で履歴を残す。
```

「確定版」と書いていないドキュメントは、実装中に AI が勝手に方針を変える余地を残す。**先に凍結する。**

## 0. 全フェーズ共通の原則

**1. 検証できないものは作らない。**
Claude は「done に見えたら止まる」。**Claude 自身が実行できる合否判定**（テスト・ビルドの終了コード・スクショ比較）が無いと、間違いに気づくのは毎回あなたになる。「動くこと」ではなく「`npm test` が exit 0」を DoD に書く。成功したと主張させず、**実行したコマンドと出力を証拠として出させる**。

**2. 唯一の真実を 1 箇所に決める。**
同じ情報を 2 箇所に書かない（実例: ARCHITECTURE.md に SKILL.md の情報ソース一覧を転記したら、件数も URL も即ズレた）。片方には「詳細は◯◯を見る」とだけ書く。

**3. コンテキストは有限。フェーズが変わったら `/clear`。**
LLM はコンテキストが埋まるほど性能が落ちる。1 → 2 → 3 → 各タスクは**それぞれ新しいセッション**で始める（ドキュメントが残っているので引き継げる）。調査は subagent に投げて、本体の会話を汚さない。同じ間違いを 2 回直させたら、直さずに `/clear` してプロンプトを書き直す方が速い。

## 1. CONCEPT.md（何を作るか）

### まず Claude にインタビューさせる
自分で書き出すより速い。プロンプト:

```
<1 行のアイデア> を作りたい。AskUserQuestion ツールで詳細に私にインタビューして。
技術・UX・エッジケース・懸念・トレードオフを聞いて。当たり前のことは聞かず、
私が考えていない難所を掘って。全部埋まったら CONCEPT.md に書き出して。
```

### 需要・競合の確認（手を動かす前にやる）
**書く前に調べる。** WebSearch で次の 3 つを確認し、**見つけた URL を CONCEPT.md に貼る**（「たぶんある」で終わらせない）。

1. **同じものが既にあるか** — 「〇〇 ツール」「〇〇 alternative」で検索。GitHub・Product Hunt・Zenn / Qiita。
2. **困っている人の声があるか** — X・Reddit・Stack Overflow・技術記事。**自分以外に 1 人も見つからないなら、需要は自分だけ**。
3. **お金が動いているか** — 有料サービスがあるなら需要の証明。無ければ「誰も欲しがっていない」か「タダでできる」のどちらか。

```
# <プロダクト名>
## 背景      なぜ自分がこれを欲しいか（1〜2 段落。ここが弱いと続かない）
## 課題      誰が、どんな場面で、何に困っているか
## 需要      同じことで困っている人がいる証拠（URL 付き）
## 競合      既にあるもの / それでも作る理由
## 解決策    それをどう解くか（2〜3 文）
## スコープ外  今回やらないこと（重要。ここが曖昧だと無限に膨らむ）
## 完成の定義  「これが動いたら v1 完成」と言える 1 文
```

判断の目安:
- **競合がゼロは良い兆候ではない。** たいてい需要が無いか、既に誰かが試して失敗している。理由を 1 行で説明できるまで掘る。
- **競合があるのは着手 OK。** ただし「自分の版はここが違う」を 1 文で言えること。言えないなら、まだ作らない。
- **需要が自分だけでも作ってよい。** ただし CONCEPT.md にそう明記する（後から「流行らない」と悩まないため）。
- **v1 は 1 機能に絞る**。迷ったら削る。

## 2. ARCHITECTURE.md（どう作るか）
`/clear` してから、CONCEPT.md を読ませて構成を決める。**選択肢とトレードオフを出し、選ぶのはユーザー**。

```
# アーキテクチャ
## 設計原則    このプロダクトで守る 3〜6 個の判断基準（迷ったらここに戻る）
## 全体の流れ  トリガー → 処理 → 出力を図で
## ファイル構成 どこに何を置くか。「作らないもの」も書く
## 技術選定    採用したもの / 捨てた対抗馬 / 理由 / 決定日 / この決定は可逆か
## データ      扱うデータと保存場所。個人情報を持つか
## 外部連携    使う API・サービスと、その料金/上限
## セキュリティ 認証方式 / シークレットの置き場 / 公開範囲
## 運用        デプロイ方法、壊れたと気づく手段
## 実装上の落とし穴  着手前に先回りして書く（下記）
## ロードマップ  Phase ごとの DoD（「これができたら次へ」）
```

### 技術選定を速くする
- **可逆な決定に時間をかけない。** 差し替えできる層（SSG・ホスティング）は後で変えられる。**データの持ち方だけは不可逆**なので、悩む時間はここに全部使う。
- **既定スタックを 1 つ持っておき、理由が無ければそれを使う**（毎回選び直さないのが最大の時短）。判断軸は「自分が止めたくなったら止められるか」＝月額が積み上がらないか。
- **決定は「捨てた案と理由」まで書く。** 半年後の自分が同じ検討を繰り返さない。
- **AI が知らない新しいライブラリを使うなら、公式ドキュメントを読ませてから書かせる**（学習データが古いと、存在しない API を自信満々に書く）。Context7 のような最新ドキュメント MCP を入れておくと事故が減る。
- **`AGENTS.md` を真実にして、`CLAUDE.md` は `@AGENTS.md` を import する薄い層にする。** AGENTS.md は Codex / Cursor / Copilot / Gemini CLI などが直接読む共通規格で、乗り換えコストが下がる（ベンダーロック対策）。

### 「実装上の落とし穴」は実際に踏む地雷を書く
架空のリスクではなく、公式ドキュメントで裏を取った具体的な罠を書く。過去に踏んだ例:
- GitHub Actions の `GITHUB_TOKEN` で push したコミットは**他のワークフローを起動しない**（無限ループ防止の仕様）。`workflow_run` で受ける。
- GitHub Pages はサブディレクトリ公開になるので `base` 設定が要る。忘れると CSS が全部 404。
- Actions の実行環境は **UTC**。cron 式は JST から 9 時間引く。

### セキュリティ既定値（毎回入れる。判断が要るのは例外だけ）
- シークレットはリポジトリに入れない（Secrets / 環境変数）。`.env.example` だけコミット。**CI に gitleaks を入れて機械的に止める**（AI は平気で鍵を書く）。
- **Actions はタグでなくコミットハッシュで固定**し、末尾に `# v7.0.0` と残す（タグは書き換え可能 = サプライチェーン攻撃の入口）。
- **AI エージェントを CI で動かすなら、信用できない入力と secrets を同じジョブに置かない。** Issue タイトル・PR 本文・コメント・コミットメッセージは**攻撃者が書ける文字列**で、エージェントはそれを指示として読む（2026 年 4 月、複数の AI レビュー Action がこの経路で secrets を PR コメントに出力させられた実例がある）。`run:` に直接埋め込まず `env:` 経由で渡し、フォークからの PR ではエージェントを走らせない。
- npm なら `.npmrc` に `strict-allow-scripts=true`。**未承認の install スクリプトを実行させない**（インストール時に任意コードが走る）。
- 依存はピン留めする（`^` を外す）。更新はまとめて月 1 回。

## 3. PLAN.md（実装計画）
`/clear` してから、CONCEPT.md と ARCHITECTURE.md を読ませて書く。**AI が迷わず上から実行できる粒度**まで割る。曖昧さが残っていたら 1〜2 に戻る。

```
## P1 — <Phase 名>
**Goal**: <これができたら次の Phase へ>

### P1-1. <タスク名>
- [ ] **やること**: <具体的な手順。コマンドがあるならそのまま書く>
- **成果物**: <作られるファイルのパス>
- **DoD**: <実行して確かめるコマンド / 目視の手順>
```

- 1 タスク = 1 PR 相当の小ささ。依存順に並べる。
- **DoD は必ず検証可能な形**にする（原則 0-1）。ここが曖昧なタスクは、実装させても必ず「できたつもり」で返ってくる。
- 完了は `- [x]`、やらないと決めたものは `- [~]` ＋理由を残す（消さない）。
- 想定と違ったタスクには **`- **実績**:` を追記**する。ここが次のプロダクトの資産になる。
- 各 Phase の末尾に**振り返り**タスクを置く（沼ったポイント・設計の穴を書き残す）。
- P1 には**足場**を必ず入れる: バージョン固定ファイル（`.tool-versions` / `mise.toml` を唯一の真実にする）、lint / format（1 ツールに寄せる）、テストランナー、CI（lint + test + build + シークレット検出）、`.gitignore`、README、`AGENTS.md`。**後から入れると全部直すことになる。**
- 最初の機能タスクは「動く最小の骨組み + デプロイ」。先に道を通してから肉付けする。
- 書き方に迷ったら `superpowers:writing-plans`。

**書けたら、実装前に 2 つのチェックを回す**（ここでの 10 分が実装の数時間を救う）:
1. **曖昧さの洗い出し** — 「この計画で判断に迷う箇所、前提が書かれていない箇所を列挙して」と聞き、埋める。
2. **整合チェック** — 「CONCEPT.md の完成の定義を満たすタスクが全部あるか、ARCHITECTURE.md と矛盾がないか検証して」。**別セッションでやる**（書いた本人は自分の穴が見えない）。

→ ここでユーザーに PLAN.md をレビューしてもらう。**承認されるまで実装に進まない。**

## 4. 実装（半自動で流す）
**タスクごとに新しいセッション**を開き、PLAN.md の該当タスクだけを渡す。**1 タスク = 1 PR。人間がレビューできる大きさを超えたら、タスクを割り直す。**

1. ブランチを切る（`start-task` skill）。方針が自明でなければ **plan mode（`Shift+Tab`）で先に読ませて計画させる**。1 文で diff を説明できる小さな変更なら plan mode は飛ばす。
2. 実装する（ロジックには `superpowers:test-driven-development`）。
3. **DoD のコマンドを実際に実行**し、出力を確認する（通ってないのに次へ行かない）。
4. **セルフレビュー**: `code-review` skill（新しいコンテキストの subagent が diff だけを見る）を回し、`git diff` も自分で読み直す。**指摘は PR を出す前に直す。**
5. PLAN.md のチェックボックスを埋め、`commit` → `create-pr`（ドラフト）。**URL を提示して、そこで止まる。**

### 速くするための道具
- **`/goal` で無人化する。** 「`npm test` が通り lint がクリーンになるまで」のような合否条件を渡すと、毎ターン別モデルが判定して、満たすまで自動で continue する。`auto` 権限モードと組み合わせると承認クリックも消える。**条件は必ず、Claude の出力から judge できる形で書く**（評価役はコマンドを実行しない）。
- **絶対に毎回やらせたいことは hook にする。** CLAUDE.md の指示は「守ってくれたらいい」程度だが、hook は決定的に実行される（例: 編集後に必ず lint、`migrations/` への書き込みを禁止）。
- **並行作業は git worktree で 2〜3 本まで。** ディレクトリを分ければ衝突しない。それ以上増やすと、レビューが追いつかず結局あなたが詰まる。

### ここから先は人間の担当
- **Ready にするのも、マージするのも人間。** Claude は `gh pr merge` を実行しない。
- マージされたのを確認してから次のタスクに進む（PR を積み上げると衝突する）。
- レビューで指摘が来たら `superpowers:receiving-code-review` で対応し、**description も最新化**する。
- 待ち時間に次のタスクを先行実装しない。**PLAN.md が正しいかどうかは、マージされた実物を見てから分かる。**

### その他
- 計画と違う実装が必要になったら、勝手に進めず **PLAN.md（必要なら ARCHITECTURE.md）を直してから**実装する。
- **認証・権限・公開範囲・CI を触る PR は「敵対的検証」にかける。** 新規セッションで、「レビューして」ではなく**「反証を試みよ」**と指示し、一次情報で裏を取らせる。ただし**レビュー役は探せば必ず何か見つける**ので、「正しさと要件に関わるものだけ挙げよ」と縛る。採否は人間が決める（過剰防御なコードが増えるのが典型的な失敗）。
- **scaffold コマンド（`create-*` 系）は既存ファイルを上書きする。** 別ディレクトリで生成し、必要なファイルだけ持ち込む。

## 5. 量産する
次のプロダクトも同じ 1〜5 を回す。持ち越すのは**ドキュメントの型と足場だけ**で、中身は毎回ゼロから書く。

- 各 Phase の振り返りを読み返す。**詰まる場所はたいてい同じ**（CONCEPT のスコープ外が甘い / DoD が曖昧 / 二重管理）。
- 繰り返し出てくる手順が見つかったら `find-automation` skill で skill 化する。
