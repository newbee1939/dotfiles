# New Product（個人開発の立ち上げ）

**設計に人間の判断を集約し、実装は自動で流す**ための skill。
判断が要るのは 1〜3 だけ。ここが甘いと 4 で必ず崩れるので、**先に進みたくなっても飛ばさない**。

3 つのドキュメントはリポジトリ直下に置く。各ファイルの冒頭に**ステータス行**を書く:

```
> **ステータス: 確定版。** 方針を変えるときは本ファイルを直し、PR で履歴を残す。
```

「確定版」と書いていないドキュメントは、実装中に AI が勝手に方針を変える余地を残す。**先に凍結する。**

## 0. 唯一の真実を決める（全フェーズ共通）
**同じ情報を 2 箇所に書かない。二重管理は必ずドリフトする**（実例: ARCHITECTURE.md に SKILL.md の情報ソース一覧を転記したら、件数も URL も即ズレた）。
片方には「詳細は◯◯を見る」とだけ書く。

## 1. CONCEPT.md（何を作るか）
ユーザーに 1 行でアイデアを聞き、**質問して埋める**（勝手に決めない）。

```
# <プロダクト名>
## 背景      なぜ自分がこれを欲しいか（1〜2 段落。ここが弱いと続かない）
## 課題      誰が、どんな場面で、何に困っているか
## 解決策    それをどう解くか（2〜3 文）
## スコープ外  今回やらないこと（重要。ここが曖昧だと無限に膨らむ）
## 完成の定義  「これが動いたら v1 完成」と言える 1 文
```

- **v1 は 1 機能に絞る**。迷ったら削る。
- 既存サービスとの違いが言えないなら、まだ着手しない。

## 2. ARCHITECTURE.md（どう作るか）
CONCEPT.md を読んだ上で構成を決める。**選択肢とトレードオフを出し、選ぶのはユーザー**。

```
# アーキテクチャ
## 設計原則    このプロダクトで守る 3〜6 個の判断基準（迷ったらここに戻る）
## 全体の流れ  トリガー → 処理 → 出力を図で
## ファイル構成 どこに何を置くか。「作らないもの」も書く
## 技術選定    採用したもの / 捨てた対抗馬 / 理由 / 決定日 / この決定は可逆か
## データ      扱うデータと保存場所。個人情報を持つか
## 外部連携    使う API・サービスと、その料金/上限
## セキュリティ 認証方式 / シークレットの置き場 / 公開範囲
## 運用        デプロイ方法、壊れたと気づく手段
## 実装上の落とし穴  着手前に先回りして書く（下記）
## ロードマップ  Phase ごとの DoD（「これができたら次へ」）
```

- **決定は「捨てた案と理由」まで書く。** 半年後の自分が同じ検討を繰り返さない。
- **可逆な決定に時間をかけない。** 差し替えできる層（SSG・ホスティング等）は後から変えられる。逆に**データの持ち方は不可逆**なのでここだけ悩む。
- **「実装上の落とし穴」は架空のリスクではなく、実際に踏む地雷を書く。** 分からなければ公式ドキュメントを引いて確認する。過去に踏んだ例:
  - GitHub Actions の `GITHUB_TOKEN` で push したコミットは**他のワークフローを起動しない**（無限ループ防止の仕様）。`workflow_run` で受ける。
  - GitHub Pages はサブディレクトリ公開になるので `base` 設定が要る。忘れると CSS が全部 404。
  - Actions の実行環境は **UTC**。cron 式は JST から 9 時間引く。
- セキュリティの既定値（**毎回入れる**、判断が要るのは例外だけ）:
  - シークレットはリポジトリに入れない（Secrets / 環境変数）。`.env.example` だけコミット。
  - **Actions はタグでなくコミットハッシュで固定**し、末尾に `# v7.0.0` と残す（タグは書き換え可能 = サプライチェーン攻撃の入口）。
  - ワークフローで**信用できない入力**（Issue タイトル、PR 本文）を `run:` に直接埋めない。`env:` 経由で渡す。
  - npm なら `.npmrc` に `strict-allow-scripts=true`。**未承認の install スクリプトを実行させない**（インストール時に任意コードが走る）。
  - 依存はピン留めする（`^` を外す）。更新はまとめて月 1 回。
- 個人開発では「自分が止めたくなったら止められるか」も見る（月額が積み上がる構成を避ける）。

## 3. PLAN.md（実装計画）
ここが本体。**AI が迷わず上から実行できる粒度**まで割る。曖昧さが残っていたら 1〜2 に戻る。

ロードマップの Phase ごとに Goal を置き、その下にタスクを並べる。

```
## P1 — <Phase 名>
**Goal**: <これができたら次の Phase へ>

### P1-1. <タスク名>
- [ ] **やること**: <具体的な手順。コマンドがあるならそのまま書く>
- **成果物**: <作られるファイルのパス>
- **DoD**: <実行して確かめるコマンド / 目視の手順>
```

- 1 タスク = 1 PR 相当の小ささ。依存順に並べる。
- **DoD は必ず検証可能な形**にする（「動くこと」ではなく「`npm test` が通る」）。
- 完了は `- [x]`、やらないと決めたものは `- [~]` ＋理由を残す（消さない）。
- 想定と違ったタスクには **`- **実績**:` を追記**する。ここが次のプロダクトの資産になる。
- 各 Phase の末尾に**振り返り**タスクを置く（沼ったポイント・設計の穴を書き残す）。
- P1 には**足場**を必ず入れる: バージョン固定ファイル（`.tool-versions` / `mise.toml` を唯一の真実にする）、lint / format（Biome など 1 ツールに寄せる）、テストランナー、CI（lint + test + build）、`.gitignore`、README。**後から入れると全部直すことになる。**
- 最初の機能タスクは「動く最小の骨組み + デプロイ」。先に道を通してから肉付けする。
- 書き方に迷ったら `superpowers:writing-plans`。

→ ここでユーザーに PLAN.md をレビューしてもらう。**承認されるまで実装に進まない。**

## 4. 実装（自動で流す）
PLAN.md を上から消化する。1 タスクごとに:

1. ブランチを切る（`start-task` skill）。実装する（ロジックには `superpowers:test-driven-development`）。
2. **DoD のコマンドを実際に実行**し、出力を確認する（通ってないのに次へ行かない）。
3. `git diff` を批判的に読み直す。バグ・考慮漏れ・過剰な複雑化・紛らわしい命名を疑う。
4. PLAN.md のチェックボックスを埋め、`commit` → `create-pr`。**PR をマージしてから次のタスクへ**（積み上げると衝突する）。

- コンテキストが枯れるので、**独立したタスクは sub-agent に投げる**（`superpowers:subagent-driven-development`）。
- 計画と違う実装が必要になったら、勝手に進めず **PLAN.md（必要なら ARCHITECTURE.md）を直してから**実装する。
- **認証・権限・公開範囲・CI を触る PR は「敵対的検証」にかける。** 作った文脈から切り離した新規セッションで、「レビューして」ではなく**「反証を試みよ」**と指示し、一次情報で裏を取らせる。指摘の採否は人間が決める（AI の指摘は過剰になりがち）。
- **scaffold コマンド（`create-*` 系）は既存ファイルを上書きする。** 別ディレクトリで生成し、必要なファイルだけ持ち込む。

## 5. 量産する
次のプロダクトも同じ 1〜5 を回す。持ち越すのは**ドキュメントの型と足場だけ**で、中身は毎回ゼロから書く。

- 各 Phase の振り返りを読み返す。**詰まる場所はたいてい同じ**（CONCEPT のスコープ外が甘い / DoD が曖昧 / 二重管理）。
- 繰り返し出てくる手順が見つかったら `find-automation` skill で skill 化する。
